## 1. 规范执行门禁（强制）

Claude 在执行任何任务前，必须按顺序通过以下 4 道门禁：

### 1.1 门禁 1：任务启动检查

当用户请求任何任务时，Claude 必须：
1. 检查是否已加载 `constitution.md`
2. 检查是否已加载适用的 `PROFILES/*.md`
3. 检查项目级 `CLAUDE.md` 是否存在
4. 确认主语言偏好（默认：中文；检查项目级覆盖）
5. ❌ 若缺失任何一项：**必须先提示用户补全，不得开始任务**

### 1.1.1 语言偏好检查

**检查顺序**：
1. 检查项目级 CLAUDE.md 是否声明了主语言偏好
2. 若未声明，使用宪法默认值（中文）
3. 若用户在会话中明确指定语言，以用户指定为准

**对话恢复/继续时的强制检查**：
- ⚠️ **重要**：当收到"对话总结"（summary）或"继续上一次对话"指令时
- **必须**：忽略 summary 中的语言，重新检查项目级 CLAUDE.md
- **禁止**：因 summary 使用英文而自动切换到英文
- **验证步骤**：
  1. 读取 CLAUDE.md 第 2 节确认语言偏好
  2. 确认后，用确认的语言回复用户
  3. 如发现偏差，立即道歉并切换语言

**语言使用要求**：
- 代码注释：使用声明的主语言
- 文档内容：使用声明的主语言
- 提交信息：使用声明的主语言
- 技术讨论：使用声明的主语言
- 代码本身：遵循语言/框架命名规范（通常英文）

### 1.2 门禁 2：关键操作门禁

以下操作前必须显式检查：修改公共 API、引入新依赖、修改目录结构、跳过测试/文档。

对每项操作：检查是否违反 constitution → ✅ 符合则说明条款 / ⚠️ 违反则警告用户并请求确认。

### 1.3 门禁 3：过程回顾

每完成一个阶段，回顾是否偏离规范 → 若发现偏离 → 立即提醒用户 → 建议纠正措施。

### 1.4 门禁 4：完成验证

任务完成后：对照规范检查所有变更 → 报告是否符合规范 → ⚠️ 若有偏差则说明偏差点和影响。

### 1.5 违规处理策略

**分级处理**：
- 🟢 轻微偏差（命名风格、注释格式）：警告，允许继续
- 🟡 中等偏差（局部重构、新增工具函数）：警告 + 说明风险，请求确认
- 🔴 严重偏差（违反宪法、破坏架构）：**必须中止**，请求用户明确指示

**警告格式**：
```
⚠️ **规范检查警告**
**检测到的偏差**：{描述}
**涉及规范**：{引用条款}
**影响**：{风险}
**建议**：A-按规范调整（推荐）/ B-继续执行（确认风险）
```

## 2. 决策优先级（冲突裁决规则）

### 2.1 加载顺序与冲突裁决顺序

**启动时加载顺序**：constitution.md → Language Profile（从 @.claude/PROFILES 查找）→ CLAUDE.md → 决定 Simple/Complex Mode → 决定是否使用 speckit 链条

**冲突裁决优先级（高→低）**：
1. constitution.md
2. BASE_CLAUDE.md（本文件）
3. 项目级 CLAUDE.md（包含规范与上下文）
4. Language Profile
5. specs / design / ADR / README / 现有代码实现

### 2.2 强制规则

- Claude **不得自行调和冲突**
- 若冲突影响实现结果，必须显式指出并请求用户裁决

### 2.3 关键决策自检

**关键决策**：新模块设计、架构调整、引入新依赖、跳过测试/文档/错误总结

**自问**：是否违反 constitution.md？是否触及不可违反条款？是否仅因"方便/省事"而妥协结构？

### 2.4 冲突处理方式

当用户要求"直接改一下就好"/"先不写测试"/"先 hack 一下：
1. 判断是否违反 Core Constitution
2. 若违反：指出违反点 → 给出合规替代方案 → 询问是否确认偏离（并记录风险）

## 3. Complex Mode 自动触发检测（强制）

### 3.1 触发条件自动检查

**必须条件**（任一为是 → 必须 Complex Mode）：
- [ ] 公共契约影响：公共 API / CLI 接口 / 配置 Schema / 数据协议
- [ ] 模块范围：≥2 个核心模块 / 跨层修改（Domain/Application/Infra）
- [ ] 结构性变更：引入新依赖 / 结构性重构 / 调整目录结构
- [ ] 风险等级：性能 / 稳定性 / 安全 / 数据正确性风险

**建议条件**（任一为是 → 建议 Complex Mode）：
- [ ] 工作量：新增文件 ≥5 个 / 修改文件 ≥10 个

### 3.2 强制触发规则

| 检测结果 | 行为 |
|----------|------|
| 无任何触发条件 | 进入 Simple Mode |
| 1-2 个建议条件 | 询问用户，建议 Complex Mode |
| 1 个必须条件 | **强制进入 Complex Mode，说明原因** |
| ≥ 2 个必须条件 | **强制进入 Complex Mode，强烈警告** |

### 3.3 无法跳过保证

**禁止跳过**：触及公共契约、存在明确风险、涉及跨≥3个模块修改

**用户要求跳过时警告**：
```
⚠️ **警告：跳过 Complex Mode 的风险**
**检测到的风险**：{列出触发条件}
**可能后果**：需求不完整返工、架构问题难修复、测试不足上线问题、技术债务累积
**建议**：A-按Complex Mode执行（推荐）/ B-收缩范围用Simple Mode / C-确认跳过（承担风险）
```
**若用户选择 C**：必须记录"⚠️ 用户选择跳过 Complex Mode，风险已告知"，并在后续关键步骤前提醒风险。

## 4. Hard Constraints（不可违反条款）

违反以下任一条，即视为 **行为错误**。

- **HC-01 复杂开发流程不可跳过**：启用时必须完整执行 clarify → plan → tasks → implement，唯一例外：用户明确声明跳过
- **HC-02 不完整需求不得静默推进**：涉及业务/安全/协议时必须 clarify 或暂停
- **HC-03 最小可合并单元原则（MCU）**：每次输出必须可作为一个 commit、对应一个明确目标，❌ 禁止混合多个无关改动
- **HC-04 公共 API 修改必须声明**：包括函数签名/schema/CLI，必须显式标注 Breaking Change 并请求用户确认
- **HC-05 新功能必须有测试策略**：要么提供测试，要么说明无法测试的原因与补救方案

## 12. 错误与经验沉淀（不可跳过）

### 12.1 触发条件（强制检查）

**自动检测触发**：开发过程中出现以下任一情况时必须检查是否需要错误总结：
1. 代码运行失败或抛出异常
2. 测试失败且需要多次调试
3. 用户报告问题或错误
4. 需要临时方案（workaround）才能继续
5. 发现非预期的行为或结果

### 12.2 触发检查流程

```
🔍 **错误触发检查**
**当前情况**：{描述当前情况}
**检查项**：是否涉及 bug/异常？是否需要 workaround？根因是否非显而易见？是否可能再次发生？
**判定**：≥2个为是→必须执行 / 1个为是→建议执行 / 0个为是→可跳过
```

### 12.3 错误总结流程（强制）

**4 个步骤**：
1. **记录错误案例**：使用 `.claude/templates/error_case_template.md`，保存到 `@.claude/knowledge/cases/{编号}-{错误名称}.md`
2. **识别错误模式**：判断是否代表一类问题 → 若是：创建/更新 `@.claude/knowledge/patterns/` 中的模式文件
3. **更新规范**（如需要）：判断是否需要更新 constitution 或 PROFILE → 添加预防性约束
4. **验证规范更新**：确保新约束已生效 → 在后续开发中优先查询

**遵循指南**：@.claude/knowledge/README.md

### 12.4 错误知识库查询（开发前必做）

在开始任何开发任务前，Claude **必须**：
```bash
ls @.claude/knowledge/patterns/           # 查询相关错误模式
cat @.claude/knowledge/patterns/*relevant* # 读取相关模式
```
**若发现相关 Pattern**：**必须**遵循其"预防性约束"，**不得**重复相同的错误

## 13. 规范执行强制要求

### 13.1 禁止绕过规范

以下行为被视为**违规**，Claude **不得**执行：
- ❌ 明知违反宪法但继续执行
- ❌ 跳过必需的规范检查
- ❌ 忽略规范冲突警告而继续
- ❌ 在用户未确认的情况下继续高风险操作

### 13.2 规范缺失的处理

当发现规范缺失或不完整时：**必须**明确告知用户 → **不得**自行推断或假设 → **建议**补充规范后再继续

### 13.3 规范冲突的裁决

当多个规范存在冲突时：**必须**按优先级裁决（constitution > BASE > CLAUDE > Profile）→ **必须**显式说明冲突点 → **不得**自行调和
