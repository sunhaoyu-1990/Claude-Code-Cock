# 代码审查流程指南（Code Review Guide）

**版本**：v1.0
**适用对象**：所有需要人工代码审查的项目
**目的**：规范人工 code review 流程，确保代码质量

---

## 概述

本指南定义了人工代码审查的标准流程、检查清单和最佳实践。

**与 AI 审查的区别**：
- **AI 审查**（c-code-reviewer）：自动化静态分析、安全检查
- **人工审查**：业务逻辑、架构设计、可维护性、团队共识

**两者结合**：AI 审查先行 → 人工审查重点 → 高效保证质量

---

## 审查流程

### 流程图

```
开发完成
    ↓
创建 PR/MR
    ↓
AI 自动审查（c-code-reviewer）
    ↓
    ├─ 通过 → 人工审查
    └─ 失败 → 修复问题 → 重新提交
            ↓
        人工审查
            ↓
        审查通过？
            ├─ 是 → 合并
            └─ 否 → 修改代码 → 重新审查
```

### 详细步骤

#### 步骤 1：创建 Pull Request / Merge Request

**PR 标题格式**：
```
feat: 添加用户认证功能
fix: 修复登录超时问题
refactor: 重构数据访问层
```

**PR 描述模板**：

```markdown
## 变更类型
- [ ] 新功能
- [ ] Bug 修复
- [ ] 重构
- [ ] 文档更新
- [ ] 性能优化
- [ ] 其他：_____

## 变更说明
{简要描述本 PR 的目的和内容}

## 影响范围
- [ ] 公共 API
- [ ] 内部实现
- [ ] 配置文件
- [ ] 数据库 Schema
- [ ] 文档

## 测试情况
- [ ] 单元测试通过
- [ ] 集成测试通过
- [ ] 手动测试通过
- [ ] 性能测试通过（如适用）

## 检查清单
- [ ] 遵循项目代码规范
- [ ] 添加必要的测试
- [ ] 更新相关文档
- [ ] 无明显性能问题
- [ ] 无安全漏洞

## 相关 Issue
Closes #<issue_number>

## 截图/演示（如适用）
{截图或 GIF 演示}
```

#### 步骤 2：AI 自动审查（可选但推荐）

**使用 c-code-reviewer agent**：

```bash
# 在 Claude Code 中调用
/skill c-code-reviewer 审查 src/auth.py
```

**AI 审查内容**：
- 输入验证与信任边界
- 文件系统与路径安全
- 命令执行与注入
- 反序列化与代码执行
- 网络、SSRF 与外部调用
- 密钥与敏感数据处理
- 依赖与供应链安全
- DoS 与资源安全
- 并发与竞态条件

**输出**：
- 安全风险列表
- 每个风险的等级（高/中/低）
- 修复建议

#### 步骤 3：人工审查

**审查者检查内容**：

1. **功能正确性**
   - [ ] 是否实现了预期功能？
   - [ ] 边界条件是否处理？
   - [ ] 错误处理是否完善？

2. **代码质量**
   - [ ] 代码是否清晰易读？
   - [ ] 命名是否规范？
   - [ ] 是否有重复代码？
   - [ ] 是否过于复杂？

3. **架构设计**
   - [ ] 模块职责是否清晰？
   - [ ] 依赖方向是否正确？
   - [ ] 接口设计是否合理？
   - [ ] 是否破坏架构分层？

4. **可维护性**
   - [ ] 是否有必要的注释？
   - [ ] 是否易于测试？
   - [ ] 是否易于扩展？
   - [ ] 是否符合项目规范？

5. **性能影响**
   - [ ] 是否有明显性能问题？
   - [ ] 数据库查询是否优化？
   - [ ] 是否有内存泄漏风险？
   - [ ] 并发处理是否正确？

6. **测试覆盖**
   - [ ] 是否有足够的单元测试？
   - [ ] 是否有集成测试？
   - [ ] 测试用例是否覆盖边界条件？
   - [ ] 测试是否易于维护？

#### 步骤 4：审查反馈

**反馈格式**：

```markdown
## 总体评价
{总体评价：LGTM / 需要修改 / 需要重大重构}

## 主要问题（必须修复）
- [ ] **问题描述**：{具体问题}
  - **位置**：{文件:行号}
  - **建议**：{修复建议}
  - **优先级**：高/中/低

## 次要问题（建议修改）
- [ ] **问题描述**：{具体问题}
  - **位置**：{文件:行号}
  - **建议**：{修复建议}

## 优化建议（可选）
- [ ] **建议**：{优化建议}
  - **原因**：{为什么建议}
  - **收益**：{预期收益}
```

**审查结论**：

- **LGTM**（Looks Good To Me）：批准合并
- **LGTM with nits**：有小问题，但可以合并后修复
- **Request changes**：需要修改后重新审查
- **Hold**：需要讨论，暂不合并

#### 步骤 5：修改与重新审查

**开发者响应**：
- 修复问题
- 在 PR 中回复修改说明
- 标记"准备重新审查"

**审查者重新审查**：
- 只检查修改的部分
- 确认问题已解决
- 给出最终结论

#### 步骤 6：合并

**合并前检查**：
- [ ] 所有审查者批准
- [ ] CI/CD 检查通过
- [ ] 测试覆盖率达标
- [ ] 文档已更新

**合并方式**：
- **Squash and merge**（推荐）：保持历史清洁
- **Merge commit**：保留完整历史
- **Rebase and merge**：线性历史

## 审查标准

### 必须修复（Blocker）

以下问题必须修复才能合并：

- 🔴 安全漏洞（SQL 注入、XSS、 CSRF 等）
- 🔴 崩溃风险（空指针、数组越界等）
- 🔴 数据丢失风险
- 🔴 性能严重下降
- 🔴 违反核心架构原则
- 🔴 缺少必要测试

### 建议修复（Should Fix）

以下问题建议修复，但不阻塞合并：

- 🟡 代码可读性问题
- 🟡 命名不规范
- 🟡 重复代码
- 🟡 测试覆盖不足
- 🟡 文档不完整

### 可选优化（Nice to Have）

以下问题可以后续优化：

- 🟢 性能微优化
- 🟢 代码风格微调
- 🟢 注释完善

## 审查最佳实践

### 审查者

1. **及时响应**
   - 目标：24 小时内完成首次审查
   - 紧急问题：优先处理

2. **建设性反馈**
   - 问题 + 原因 + 建议
   - 避免主观评价
   - 提供示例代码

3. **关注重点**
   - 大问题优先于小问题
   - 架构优先于实现
   - 逻辑优先于格式

4. **解释原因**
   - 为什么这是个问题？
   - 不修复的风险是什么？
   - 有更好的做法吗？

### 开发者

1. **小而聚焦的 PR**
   - 单个 PR ≤ 400 行代码变更
   - 一个 PR 只做一件事
   - 避免巨型 PR

2. **清晰的描述**
   - 说明"为什么"做
   - 说明"如何"实现
   - 提供测试/截图

3. **自我审查**
   - 提交前自我审查
   - 使用 AI 工具辅助
   - 减少低级错误

4. **积极回应**
   - 及时响应审查意见
   - 解释设计决策
   - 接受合理建议

## 审查清单模板

### 功能变更

```markdown
## 功能审查
- [ ] 是否实现了所有需求？
- [ ] 边界条件是否处理？
- [ ] 错误处理是否完善？
- [ ] 是否向后兼容？

## 代码审查
- [ ] 代码是否清晰？
- [ ] 命名是否规范？
- [ ] 是否有重复代码？
- [ ] 复杂度是否合理？

## 测试审查
- [ ] 单元测试是否充分？
- [ ] 集成测试是否覆盖？
- [ ] 测试是否可维护？

## 文档审查
- [ ] API 文档是否更新？
- [ ] README 是否更新？
- [ ] 注释是否充分？
```

### Bug 修复

```markdown
## 问题确认
- [ ] 根因是否找到？
- [ ] 修复是否彻底？
- [ ] 是否有回归风险？

## 修复审查
- [ ] 修复是否正确？
- [ ] 是否引入新问题？
- [ ] 测试是否覆盖修复点？

## 验证审查
- [ ] 是否有回归测试？
- [ ] 是否有复现步骤？
- [ ] 是否有验证结果？
```

### 重构

```markdown
## 目标确认
- [ ] 重构目标是否清晰？
- [ ] 范围是否合理？

## 重构审查
- [ ] 行为是否保持一致？
- [ ] 是否有测试保护？
- [ ] 是否逐步重构？

## 结果审查
- [ ] 代码质量是否提升？
- [ ] 可维护性是否改善？
- [ ] 性能是否保持或提升？
```
