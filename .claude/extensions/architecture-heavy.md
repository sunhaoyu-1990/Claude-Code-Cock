# Extension: architecture-heavy

**层级**：Extension（可选加载，重型约束）  
**启用条件**（满足任一项建议启用）：
- 项目存在 ≥3 个核心子系统或清晰分层（domain/application/infrastructure 等）
- 核心模型/协议长期演进，需要强一致性治理
- 变更风险高（线上系统、基础库、平台组件）

**依赖**：需先导入 `BASE_CLAUDE.md`（组织级），建议导入 `PROFILES/common.md`

---

## 1️⃣ 架构目标（本扩展的“为什么”）

- 保持分层清晰，避免“能跑就行”的耦合扩散
- 保持核心契约稳定，减少破坏性变更
- 确保变更可审查、可追踪、可回滚

---

## 2️⃣ 分层规则（强约束）

> 你需要在项目中把分层名称替换为真实分层（或补充）。

### 推荐分层（示例）
- **Domain**：核心业务模型、纯逻辑、无外部依赖
- **Application**：用例编排、服务层、事务边界
- **Infrastructure**：数据库/网络/外部系统适配
- **Interface/Adapters**：API/CLI/UI/消息消费等入口

### 强制约束
- **禁止**：跨层“逆向依赖”（例如 Domain 依赖 Infrastructure）
- **禁止**：入口层直接调用 Infrastructure 绕过 Application（除非项目明确允许）
- **允许**：通过接口/抽象（ports）实现依赖反转

---

## 3️⃣ 核心契约（Contract）治理

### 必须显式声明的“核心契约”
- 公共 API（函数/类/模块）
- 配置 schema（YAML/JSON/ENV）
- 数据协议（消息、HTTP、文件格式）

### 变更规则（与 BASE 配套）
- 对核心契约的变更：
  - 必须列出影响面
  - 必须提供兼容策略（向后兼容 / 迁移路径）
  - 若为 Breaking：必须请求用户确认

---

## 4️⃣ 模块边界与目录规则（MCU 友好）

- 新增模块前必须回答：
  1) 属于哪一层？
  2) 边界是什么？
  3) 与相邻模块通过什么契约通信？
- 禁止“顺手”把不相关代码塞进同一目录/同一模块。

---

## 5️⃣ 变更评审输出规范（启用本扩展时建议使用）

Claude 在输出实现方案/变更时，增加以下小节（简短即可）：

- **层级定位**：本变更属于 {Domain/Application/...}
- **契约影响**：是否影响公共 API / schema / 协议？
- **依赖方向**：是否引入新的依赖边？
- **回滚策略**：如何撤销本次变更？
